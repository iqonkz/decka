# ARCHITECTURE.md — архитектура Decka

Дата проектирования: 2026-11-14. Пометка `[unverified]` — факт не проверен по первоисточнику в ходе проектирования.

## 1. Что это

Decka превращает старый Android-телефон в настольную панель для Windows-ПК: сетка кнопок 5×3 и живые виджеты (состояние ПК, статусы сервисов, уведомления по webhook). Действия исполняет только ПК; телефон — тонкий экран, который знает лишь идентификаторы действий.

Целевое устройство тестов: Samsung Galaxy S9, Android 10 (API 29), AMOLED 2960×1440, альбомная ориентация. ПК: Windows 10/11 x64.

### 2.2 Что отсутствует у аналогов (по изученным страницам)

- Ни один из изученных проектов не описывает работу телефона по USB-кабелю без сети `[unverified — отсутствие упоминания не доказывает отсутствие функции]`.
- Ни один не описывает защиту OLED-экрана от выгорания как функцию `[unverified — то же]`.
- Desko принимает данные от редактора (POST от расширения VS Code), но общего webhook-API для произвольных скриптов с токеном не описывает; аутентификации нет.

### 2.3 Три отличия, закреплённые в MVP

1. **USB-режим (`adb reverse`).** Телефон работает по кабелю без Wi-Fi; в режиме «только USB» агент слушает `127.0.0.1` и не открывает ни одного порта в локальную сеть. Задачи T7.4, T7.5, T6.8.
2. **Защита AMOLED от выгорания.** Чисто чёрный фон, сдвиг пикселей, затемнение по бездействию, заставка с блуждающими часами, ночной режим, заставка при недоступном ПК. Задачи T8.1–T8.3.
3. **Webhook-first для разработчика.** `POST /api/notify` (в том числе `text/plain` одной командой curl) и `POST /api/status` с TTL — статусы деплоев и ИИ-сессий без плагинов; встроенные HTTP-проверки «моих сервисов». Задачи T5.1, T5.2, T5.4, T9.2.

## 5. Потоки данных

### 5.1 Сопряжение

1. Пользователь в окне настроек нажимает `Pair a new device` → `start_pairing` → ядро создаёт код (TTL 120 с) и QR с URL (PROTOCOL.md §8).
2. Телефон сканирует QR (в приложении — встроенным сканером; без приложения — системной камерой, которая открывает веб-клиент, отданный агентом).
3. Клиент открывает WS, шлёт `pair` с кодом → получает `paired` (токен устройства) и `welcome`.
4. Клиент сохраняет `{token, deviceId, hosts, port, agentName}` в `localStorage`. Агент хранит только SHA-256 токена.

### 5.2 Состояние и рассылка (идея: Desko)

- `Store` держит пять секций: `layout`, `sys`, `statuses`, `notifications`, `vars`.
- Любой источник (сборщик, HTTP API, наблюдатель файлов, действие с `toggleVar`) вызывает `set(section, value)`. Если значение глубоко равно текущему — ничего не происходит. Иначе `rev += 1` и всем подписчикам уходит `patch` с полным новым значением секции.
- Сборщики округляют значения (CPU до целого, uptime до минуты, время ответа до 10 мс), чтобы шум не порождал рассылку.
- Сборщик `sys` пропускает итерации, когда нет ни одного подключённого клиента.
- Новый клиент: подписка → снимок → `welcome`; патчи с `rev` ≤ `rev` снимка отбрасываются.
- Отставший подписчик (переполнение broadcast-буфера на 64 сообщения) отключается; клиент переподключается и получает свежий снимок.

### 5.3 Нажатие кнопки

`pointerup` на кнопке → `controller.press(actionId)` → WS `press {id, actionId}` → ядро: лимит 20/с → поиск действия в памяти (из `actions.json`) → `ActionRunner.run` в blocking-пуле → при успехе и `toggleVar` обновление секции `vars` → `press_result`. Клиент показывает `ok`/`error`. Вид кнопки с `bind` меняется, когда приходит `patch` секции `vars`, — у всех подключённых клиентов одновременно.

### 5.4 Уведомления и статусы

Скрипт → `POST /api/notify` или `/api/status` с `Authorization: Bearer <apiToken>` → проверка токена и лимитов → изменение секции → `patch` клиентам → тост и лента / список статусов. HTTP-проверки (`collectors.checks`) пишут в ту же секцию `statuses` с `source: "check"`.

### 5.5 USB-режим

- Условие: на ПК установлен adb (Android platform-tools), на телефоне включена отладка по USB и ПК авторизован.
- Агент при `usb.enabled` каждые 5 с выполняет `adb devices` и для каждого нового устройства в состоянии `device` — `adb -s <serial> reverse tcp:<port> tcp:<port>`. Раз в 60 с список проброшенных сбрасывается (самовосстановление после сна ПК, переподключения кабеля, перезапуска adb-сервера).
- Клиент в приложении Capacitor всегда пробует `127.0.0.1:<port>` первым (таймаут 1,5 с), затем сохранённые LAN-адреса. Никакого определения «подключён ли кабель» на телефоне нет — успешное соединение с `127.0.0.1` и есть признак USB.
- Тот же токен устройства действует на обоих транспортах. Сопряжение по USB возможно без Wi-Fi (клиент при сопряжении тоже сначала пробует `127.0.0.1`).
- Режим «только USB»: `bind = 127.0.0.1` — порт не виден в локальной сети.
- adb не входит в состав Decka и не скачивается автоматически.

### 5.6 Защита AMOLED (клиент)

Режимы экрана: `active` → `dim` → `sleep`. Параметры — `layout.display` (управляются с ПК).

| Механизм | Поведение |
|---|---|
| Чёрный фон | `#000` везде; плитки тёмные; постоянных ярких надписей нет (индикатор канала связи показывается 4 с) |
| Pixel shift | каждые 60 с весь интерфейс смещается по траектории Лиссажу в пределах ±4 px, переход 2 с |
| Затемнение (`dim`) | бездействие ≥ `dimAfterSec` → чёрный слой с непрозрачностью `1 - dimLevel` |
| Заставка (`sleep`) | бездействие ≥ `sleepAfterSec`, либо ночной интервал, либо ПК недоступен ≥ 30 с → чёрный экран, серые часы меняют место каждые 30 с; показывается `PC offline` и число статусов в `error` |
| Пробуждение | первое касание только будит (не нажимает кнопку); уведомления `warning`/`error` будят экран; `info`/`success` в заставке экран не будят |
| Порядок правил | `computeMode` в T8.1 (активность < 10 с всегда даёт `active`) |

Яркость подсветки аппаратно не меняется (плагины яркости не используются): на AMOLED чёрный слой даёт тот же эффект, так как чёрные пиксели не светятся.

### 5.7 Жизненный цикл и сон ПК

- Агент стартует с Windows (автозапуск с аргументом `--minimized`), живёт в трее. Закрытие окна не завершает процесс.
- ПК уснул: сокеты рвутся. Клиент уходит в `offline`, через 30 с — в заставку `PC offline`, и бесконечно переподключается с задержкой до 15 с.
- ПК проснулся: агент продолжает работу (отдельной обработки событий питания нет); мёртвые соединения закрываются по таймауту тишины 30 с; USB-проброс восстанавливается циклом adb ≤ 60 с.
- Порт занят при старте: агент не падает, окно настроек показывает ошибку и кнопку `Retry`.

## 6. Модель безопасности

### 6.1 Границы доверия

| Сторона | Уровень доверия |
|---|---|
| Файлы в `%APPDATA%\Decka` и окно настроек | Доверенные (права пользователя Windows). Кто может писать `actions.json`, тот уже может исполнять код от имени пользователя |
| Сопряжённый телефон | Ограниченное доверие: может вызвать **любое из заранее определённых** действий по id и закрыть уведомление. Больше ничего |
| Держатель `apiToken` | Может добавлять уведомления, статусы и переменные. Не может исполнять действия |
| Локальная сеть | Недоверенная: трафик не шифруется, предполагается возможность прослушивания |
| Веб-страницы в браузере на ПК | Недоверенные: могут пытаться обращаться к `localhost:9247` |

### 6.2 Сопряжение

- Не более одного активного кода. Код: 8 символов из 32-символьного алфавита (40 бит), из криптографического генератора ОС.
- Срок жизни 120 с; одноразовый; после 5 неверных попыток код уничтожается.
- Лимит: 10 сообщений `pair` в минуту с одного IP.
- Сравнение кода — за постоянное время. Причина отказа клиенту не раскрывается.
- Код создаётся только действием пользователя в окне настроек или из меню трея.
- Код в QR находится во фрагменте URL (`#`) и не попадает в HTTP-запрос.

### 6.3 Токены

| Токен | Формат | Где хранится | Отзыв |
|---|---|---|---|
| Токен устройства | 32 случайных байта, base64url (43 символа) | На телефоне — `localStorage`; на ПК — только SHA-256 в `devices.json` | Поштучно, `Revoke` в окне настроек; живые сокеты закрываются сразу |
| `apiToken` | `dk_` + 43 символа | `config.json` открытым текстом (его нужно показывать пользователю) | `Regenerate` |

Токен устройства передаётся первым сообщением WS, а не в URL — не попадает в логи и историю.

### 6.4 Угрозы и меры

| № | Угроза | Мера | Остаточный риск |
|---|---|---|---|
| S1 | Скомпрометированный или чужой клиент пытается исполнить произвольную команду | В протоколе нет сообщения, несущего команду; `press` несёт только `actionId`; лишние поля игнорируются; тест `extra_fields_are_ignored` | Клиент может вызвать любое определённое действие — пользователь сам решает, что класть в `actions.json` |
| S2 | Устройство в той же сети подключается без сопряжения | Любое сообщение до `pair`/`hello` → закрытие 4401; таймаут рукопожатия 5 с | — |
| S3 | Перебор кода сопряжения | 40 бит, TTL 120 с, 5 попыток на код, 10 попыток/мин на IP, код существует только по действию пользователя | Пренебрежимо мал |

### 6.5 Особенности WebView

- Capacitor настроен на `androidScheme: "http"` и `cleartext: true`; в манифесте `usesCleartextTraffic="true"`. Со схемой `https` WebView запретил бы `ws://` как смешанный контент.
- Источник (origin) приложения — `http://localhost`; он включён в белый список `Origin` для WS.
- Веб-клиент по `http://<LAN-IP>` — небезопасный контекст: недоступны service worker, Wake Lock, камера. Поэтому основной клиент — APK; веб-режим — для быстрой пробы и для USB (`http://localhost` — безопасный контекст).

## 9. Критерии готовности MVP

1. Установщик NSIS ставит агент; агент стартует в трей и переживает перезагрузку Windows (автозапуск).
2. S9 сопрягается по QR за одно сканирование; повторный запуск приложения подключается без действий пользователя.
3. Все 5 типов действий исполняются с телефона; кнопка с `bind` меняет вид.
4. Виджеты `clock`, `sys`, `statuses`, `status`, `notifications` показывают живые данные.
5. `curl` на `/api/notify` даёт тост ≤ 1 с; `/api/status` с TTL работает.
6. USB-режим: работа без Wi-Fi; режим «только USB» закрывает порт от сети.
7. Защита экрана: затемнение, сдвиг, заставка, ночной режим, заставка при недоступном ПК.
8. После сна ПК связь восстанавливается без действий пользователя.
9. Все автоматические тесты зелёные; `MANUAL_CHECKS.md` без `FAIL`.

Вне MVP: плагины, пользовательские иконки-картинки, TLS, mDNS, несколько ПК на один телефон, macOS/Linux-агент, iOS-клиент, мульти-действия и макросы, слайдеры, drag-and-drop в редакторе, локализация интерфейса, автообновление.

## 10. Итог проверки плана

План пройден от T0.1 до T9.4 с позиции исполнителя, который следует тексту буквально и работает в Windows PowerShell 5.1. Это проверка чтением: ни одна команда не запускалась, код не писался. Найдено и исправлено в документах:
