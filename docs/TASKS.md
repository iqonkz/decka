# TASKS.md — открытые задачи Decka

Исполнитель: Claude Sonnet 5.5. Каждая задача — 1–2 часа. Задачи выполняются строго по порядку. Архитектурных решений исполнитель не принимает: всё решено в `/docs`. Перед каждой задачей прочитай `docs/QUICKREF.md` и только те разделы, на которые задача ссылается.

## 0. Правила исполнителя

1. **Оболочка — Windows PowerShell 5.1.** `&&` и `||` не работают: команды разделяй `;`. Вместо `curl` пиши `curl.exe`. Все команды запускаются из корня репозитория, если не сказано иное. Блок «Проверка» запускается **одним вызовом** (переменные между вызовами не сохраняются).
2. **Версии.** Ставь ровно те версии, что указаны в задаче (`npm install pkg@x.y.z`, `cargo add crate@x.y.z`). Где версии нет и стоит пометка «последняя» — `npm install pkg` / `cargo add crate` без версии. Версию и набор библиотек не менять.
3. **Если API библиотеки отличается от имён в плане** — открой документацию ровно установленной версии (`https://docs.rs/<crate>/<version>`, README пакета) и используй эквивалент. Это не архитектурное решение. Поведение, описанное в `/docs`, менять нельзя.
4. **Если шаг невыполним или документы противоречат друг другу** — не выбирай сам. Запиши в `docs/BLOCKERS.md` (номер задачи, что именно, что пробовал) и остановись.
5. **Безопасность (MUST):** в коде клиента и в протоколе не должно появиться ни одного пути, по которому телефон передаёт команду, путь, аргументы, клавиши или URL для исполнения. Телефон шлёт только `actionId`.
6. Приоритет документов при расхождении: `PROTOCOL.md` > `DATA_MODEL.md` > `ARCHITECTURE.md` > `TASKS.md`. О расхождении — запись в `BLOCKERS.md`.
7. После каждой задачи: все команды «Проверки» прошли → `git add <свои пути>; git commit -m "T<номер>: <название>"` (никогда `git add -A` / `git add .` — в дереве могут быть незакоммиченные правки архитектора в `docs/`). Не коммить `.tmp/`, `target/`, `node_modules/`, `dist/`.
6a. **Правки архитектора в `docs/` и `CLAUDE.md` никогда не откладывать (`git stash`), не откатывать (`git checkout`/`restore`) и не перезаписывать.** Первым шагом любой работы: `git add docs CLAUDE.md AGENTS.md; git commit -m "docs: ..."`. 2026-11-21 правки по голосу были отложены в stash и чуть не потерялись.
7a. **Экономия токенов.** Вывод сборки и тестов не показывай целиком: `| Select-Object -Last 20` или только строки с ошибками. Снимки экрана открывай только когда их нужно оценить. Архив `docs/archive/` целиком не читай — только поиск по номеру задачи. Новая сессия (`/clear`) после каждой одной-двух задач: состояние восстанавливается из `CLAUDE.md`, `QUICKREF.md`, `git log`.
7d. **Быстрые задачи, сборка — раз в крупный выпуск (решение владельца 2026-11-21, главнее блоков «Проверка» в задачах).** Задачи делаются как обычно, ориентир — порядка 5 минут на задачу. Жёсткого лимита нет, дробить на шаги не нужно.
- **В обычной задаче:** `npm run typecheck` и тесты затронутых модулей (п. 7c). Release-сборки (`release:agent`, `release:apk`), установщик, APK, снимки, полный `npm test`, весь `cargo test` — **не делать**: release-сборка одна идёт ≈ 20 минут.
- **Сборка, полный прогон, снимки, аудит и выпуск — только в задаче «Стабилизация» перед выпуском 0.x.0** (`T<этап>.S`), исправление всего упавшего — там же.
- Строки «Проверка» в задачах, где есть сборка, читать так: сборка — только в стабилизации.
- **Когда делать сборку, полный прогон или стабилизацию, решает архитектор по отчётам** и пишет это в промпте явно («сделай тестовую сборку APK», «полный прогон», «T21.S»). Без такого указания — не делать.
7e. **Исправления — отдельно от выпуска (решение владельца 2026-11-22: «маленькое изменение делается полчаса»).**
- **Исправление** = код + тест на этот случай + `cargo test -p decka-core <модуль>` / `npx vitest run <файл>`. Без release-сборки, без полного прогона, без запуска серверов моделей (кроме случая, когда баг именно в них и иначе не воспроизвести), без живых проверок «на всякий случай». Коммит и отчёт ≤ 5 строк. Цель — 5–10 минут.
- **Выпуск** (`release:agent`, `release:apk`, хеши, latest.json) — отдельной командой «выпуск 0.x.y», когда архитектор её даёт, и собирает **все накопленные** исправления за раз. APK собирать, только если менялся `client/` или `shared/`.
- Если владельцу нужно проверить исправление до выпуска — по команде «тестовая сборка»: только `release:agent` (установщик ПК), без APK и без хешей.
7c. **Не тестировать долго то, что и так работает (решение владельца 2026-11-20).**
- В обычной задаче: `npm run typecheck` и **только тесты затронутых модулей** — `npx vitest run <пути к тестам>`, `cargo test -p decka-core <имя_модуля>`. Новые тесты задачи пишутся как обычно.
- Ручные прогоны, снимки и запуск агента для уже принятых функций не делать.
- Полный прогон (`npm test`, весь `cargo test -p decka-core`), аудит, снимки и проверка релиза — **один раз, перед выпуском 0.x.0**. Упало что-то старое → исправить там же, до выпуска.
- Строки «Проверка» в задачах, где стоит полный прогон, читать так: полный — только в задаче выпуска.
7b. **Место на диске.** Перед отчётом проверяй размер `target\debug` (`(Get-ChildItem target\debug -Recurse -File | Measure-Object Length -Sum).Sum / 1GB`). Больше 20 ГБ — `cargo clean --profile dev` (только когда никакая сборка не идёт). `target\release` не чистить. 2026-11-19 папка доросла до 92 ГБ.
8. Тексты интерфейса — на английском (с T14.7 — через словари `en`/`ru`, DESIGN.md §6). Комментарии в коде — на английском, только там, где логика неочевидна.
9. Тесты, не требующие железа, обязательны там, где они перечислены. «Ручная проверка» выполняется исполнителем, если у него есть доступ к экрану/устройству; иначе пункт переносится в `docs/MANUAL_CHECKS.md` (номер задачи + текст пункта) для владельца, задача считается выполненной при прохождении автоматических проверок.
10. Каталог `/docs` не редактировать, кроме файлов, явно названных в задачах (`BLOCKERS.md`, `MANUAL_CHECKS.md`, `RECIPES.md`, `TESTING.md`).

### T20.4 — Обновление приложения на телефоне с ПК
1. **Агент:**
   - узнав о новой версии, скачивает APK из того же релиза;
   - проверяет SHA-256 по `SHA256SUMS.txt` и подпись этого файла: `release:apk` подписывает `SHA256SUMS.txt` тем же ключом обновлений → `SHA256SUMS.txt.sig`; агент проверяет его публичным ключом из сборки через `tauri-plugin-updater`/`minisign-verify`. **Если в зависимостях нет готовой проверки — BLOCKERS, не писать свою.**
   - хранит APK в `%LOCALAPPDATA%\Decka\updates\`.
2. **Протокол:** в `welcome`/`patch` — секция `update: { app?: { version, size } } | null`. Скачивание — внутри зашифрованного канала, сообщениями `apk_get{offset}` → `apk_chunk{offset, data}` кусками по 3000 байт (base64 укладывается в кадр). Только для сопряжённых устройств, не чаще одной загрузки на устройство одновременно. Типы — PROTOCOL.md §3 (`ApkGetMsg`, `ApkChunkMsg`, `UpdateInfo2`).
3. **Телефон:**
   - баннер в меню телефона `Update Decka to 0.11.0` → загрузка с прогрессом → проверка SHA-256 на телефоне → установка;
   - установка — своим маленьким плагином: `FileProvider` + `ACTION_VIEW` с `application/vnd.android.package-archive`, разрешение `REQUEST_INSTALL_PACKAGES`; Android сам спросит «Разрешить установку из этого источника» в первый раз;
   - подпись APK та же (T19.6), поэтому установка идёт поверх, без потери сопряжения.
4. **Тесты:** сборка APK из кусков и проверка SHA-256 (фикстура); отказ при несовпадении; лимит одной загрузки.
